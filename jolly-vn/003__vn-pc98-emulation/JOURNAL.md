## Business Goal

This folder began as the game-design work for a procedurally generated visual novel starring Jolly, Meta Muse's mascot, building on the character reference (v4 sheet) and the PC-98 visual-novel concept from 001. In practice the branch diverged from that goal: instead of settling the game's design, the work became a feasibility investigation into whether the visual novel could run as a genuine PC-98 program inside a browser tab. The folder has therefore been renamed from `003__vn-game-design` to `003__vn-pc98-emulation` so that its name describes the question that was actually explored, and the design questions from the original goal remain open rather than answered.

## Technical Uncertainty

The uncertainty that consumed this branch was whether real PC-98 emulation is a practical target for the Jolly visual novel today. That question breaks down into whether the Suika3 engine can boot unattended under the WebNP2 browser emulator, whether backgrounds, sprite, text, and choices render correctly once it does boot, whether a player can actually operate the game with the keyboard and mouse that a browser supplies, and whether a generated second chapter can be delivered to the running game at the chapter boundary. A secondary uncertainty, which only became visible after the work was under way, was how much of the total effort would be spent simply waiting for the emulated machine to boot and load, because every test of a change required another full boot cycle.

## Technical Configuration

The prototype lives in `prototype/` and pairs a self-hosted WebNP2 player (Neko Project II kai compiled to WebAssembly) with a Suika3 engine binary compiled from upstream source using the `pc98` preset. The guest boots FreeDOS(98) from a floppy image whose AUTOEXEC launches the engine from a FAT hard-disk image, and the game data is packed into the engine's own `assets.arc` package because DOS cannot open the longer paths used by the message-box assets. The emulator needs its CPU clock multiplier set to 32 before the guest runs at a usable speed, and the engine itself carries a set of reliability patches, described in `prototype/README-EMULATION.md`, that retry or verify disk reads because reads under this emulator intermittently return corrupted bytes. The character and style anchors did not change during this branch: the character anchor remains `000__find-jolley-assets/outputs/jolly-character-sheet-v4.webp`, and the style anchor remains the v3 recipe in `001__stylized-pc98-jolly-visual-novel-concept`, although neither was exercised further here.

## Technical Exploration

The exploration began in the wrong place, because the first prototype was a JavaScript imitation that parsed Suika-like tags itself rather than running any PC-98 software. That approach was rejected as soon as it was inspected, since it proved nothing about emulation, and the work restarted around the real WebNP2 player. From that point the investigation proceeded as a sequence of boot failures, each of which had to be diagnosed from screenshots: a blank screen after the memory check, a DOS/4GW stub failure because the extender was not where the stub looked for it, the game executable not being found on the hard disk, and a screen of moving white bars under one extender configuration. Because the human tester was initially relaying every screenshot by hand, the agent had no direct view of the machine, and a considerable part of the effort went into building headless browser probes that could boot the emulator, read its text and graphics memory, and record what the guest had actually done.

Once those probes existed, the underlying fault became clear: the emulated disk path returns corrupted bytes often enough that the official engine binary could not boot reliably, since a single garbled read could poison the configuration, the archive index, or a PNG image. The response was to rebuild the engine with retry-and-verify behaviour at each layer and to increase the emulator clock, after which Chapter 1 did render and play in automated runs: the matsuri background, the Jolly sprite, the message box, and both endings of the apple-candy and cotton-candy choice were all reached, and generated second chapters were completed through both a floppy hot-swap and a reboot disk, as the screenshots in `screenshot/screen-working-1.jpg` and `screenshot/screen-working-2.jpg` show. The graphics, however, remain far from finished, because the PC-98 graphics driver posterizes colour aggressively, so Jolly reads much redder than her source art and the backgrounds lose most of their shading.

The human experience did not match the automated result. A person opening the page could not tell how to operate the game: mouse clicks do nothing because the PC-98 input layer only ever polls the keyboard, and although the emulator's virtual keyboard could advance the text, choice selection could not be made to work from the tester's seat. Automated keyboard input (Enter to advance, arrow keys to point at a choice, Enter to confirm) succeeded in headless runs, but a control scheme that only the agent can operate has not been demonstrated to be usable, so the correct conclusion is that functionality remains unproven for a human player. The fourteen hours this branch consumed were mostly a consequence of the test loop itself, since each verification required booting the emulated machine and waiting minutes for it to load, which made even small changes expensive to confirm.

## Technical Goal

The original goal, a written game-design template ready to drive procedural generation, was not reached and should not be recorded as progressed by this branch. What the branch produced instead is a feasibility record: a working-but-unpolished emulation prototype in `prototype/`, the boot and chapter-delivery evidence described above, and a clear statement of the costs that a real PC-98 port would carry. Any future design work should resume from the original questions in a separate branch rather than treating this prototype as a foundation, because its value is in what it ruled out, not in code that the game should inherit.

## Technical Conclusion

Real PC-98 emulation in the browser is technically feasible, in the narrow sense that the engine boots, renders, and completes chapters under WebNP2, but it is not a practical way to build this visual novel now. The input model is undiscoverable for a human player, the graphics need substantial rework before they represent the intended art, and the boot-and-load cycle makes iteration so slow that ordinary development becomes impractical. The decision is therefore to build the visual novel so that it looks like a PC-98 game, using conventional technology that renders and responds immediately, and to defer any genuine PC-98 port until there is a specific reason to pay its costs again. The emulation prototype is preserved in this folder as evidence for that decision rather than as a starting point.

One methodological observation is recorded for later experimentation, without being adopted here: single-shotting a prompt against a stated goal allowed the work to drift from game design into an open-ended feasibility slog, and a more deliberate methodology for framing such goals — with explicit stopping conditions and a fast verification loop agreed in advance — might have reached the same conclusion in far less time. Whether that is true is itself an experiment for a later branch.

## Open Questions / Future Experiments

- Which conventional engine or web stack reproduces the PC-98 presentation — the large cropped portrait, the full-width dialogue box, and the decorative borders — with the least friction, now that genuine emulation is deferred?
- The original design questions remain open: how much of the branching is hand-authored versus generated, how Jolly is kept on-model across generated scenes, and how character consistency and text legibility are regression-checked per beat.
- If a real PC-98 port is ever resumed, it first needs a human-operable input scheme, a deliberate 16-colour art pipeline instead of salvaged screenshots, and a test loop that does not require a full boot for every change, since those three costs dominated this branch.
- A later methodology experiment could test whether a tightly framed goal with predefined evidence and stopping conditions produces the same conclusion faster than an open-ended prompt did here.
